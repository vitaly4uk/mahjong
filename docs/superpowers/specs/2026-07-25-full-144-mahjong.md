# Full 144-tile mahjong: flowers/seasons, oblique tile set, native rendering

Date: 2026-07-25. Status: implemented.

## Problem

The game was a riichi set of **136 tiles** (34 kinds × 4) on the Turtle layout,
**deliberately trimmed from 144 to 136** (see
[2026-07-16-turtle-board-shape-design.md](2026-07-16-turtle-board-shape-design.md)):
the 3 "head/tail" protrusions on layer 0 and the 5-tile "peak" (layers z=3, z=4)
were removed. In a real mahjong set those 8 cells are occupied by **4 flowers +
4 seasons** matched as wildcards. The reason for the trim back then was that the
FluffyStuff set (CC0) had no flower/season art, and adding a separate one for
just 8 tiles was deemed not worth it.

Now the task is a **full 144-tile mahjong**. This reverses the 2026-07-16 decision.

## Solution

### Shape (144 tiles, 5 layers)

The full Turtle shape has been restored: `WIDTH 12→14`, `LAYERS 3→5`, layer
breakdown **87 / 36 / 16 / 4 / 1 = 144** (`gameplay/board.py` +
`static/game/board.js`, mirrored). The shell is shifted to the center of the
14-wide grid, and the "head/tail" protrusions (layer 0) and the central "peak"
(z3 2×2 above the 16-cell z2, z4 the apex) have been added back. The original
Turtle was on a half-tile grid with half-tile protrusions, so the exact
coordinates of the 8 restored cells are an integer approximation (verified
visually; the module's self-check fails if the total ≠ 144).

### Wildcard matching (two groups)

8 bonus kinds: flowers `Plum/Orchid/Bamboo/Chrysanthemum`, seasons
`Spring/Summer/Autumn/Winter`. Matching uses **two groups** (classic KMahjongg
behavior): any flower ↔ any flower, any season ↔ any season. Implemented via a
shared `match_key`/`matchKey` helper (all flowers → `'flower'`, all seasons →
`'season'`, everything else — its own kind); `can_match`/`canMatch` and
`find_matching_pair`/`findMatchingPair` compare `match_key`, not `kind`. Deck:
34 regular kinds × 4 copies (68 pairs) + 4 flowers + 4 seasons (1 copy each,
dealt as 2 different-within-group pairs) = **72 pairs = 144 tiles**. The
generator (`gameplay/generator.py`) lays out pairs as `(kindA, kindB)`: for
regular tiles `(k, k)`, for bonus tiles two different kinds from the same
group; the reverse simulation guarantees solvability (checked on 30 seeds ×
3 levels).

### Art: a ready-made oblique tile set (replacing the hand-built body)

Source — **Wikimedia's "SVG Oblique illustrations of Mahjong tiles" by
User:Cangjie6**, the full set of 42 kinds in oblique-3D projection,
**CC BY-SA 4.0** (attribution + share-alike; see
`static/game/tiles/CREDITS.md`). The SVGs were cleaned of Adobe metadata
(`<!DOCTYPE>`/DTD, `<!ENTITY>`, `<switch>`/`<foreignObject>`) —
`<foreignObject>` was "tainting" the WebGL canvas, blocking rasterization; the
art itself (paths/colors) was not changed. Name mapping: `MJw→Man`, `MJt→Pin`,
`MJs→Sou`, `MJf→winds`, `MJd→dragons`, `MJh1-4→seasons`, `MJh5-8→flowers`.

Since the sprite already contains the whole tile with its volume drawn in,
**the hand-built 3D body has been removed** (`tileBody`+`Front`+side-face
geometry): one tile = one sprite. The pseudo-3D stacking remains — layer
offset (`LAYER_DX/DY`, a fraction of the tile size) + depth sorting
`z*10000 + y*100 + (WIDTH-1-x)`.

### Native rendering + runtime rasterization (Scale.NONE)

Goal — tile sharpness at any window size/DPI. `Scale.FIT` (fixed internal
resolution + CSS stretch) limited that (stretching a large window = blur). We
switched to **`Scale.NONE` with manual DPR scaling** (`resizeCanvas`): backing
size = CSS size × dpr, CSS size = the container → **world coordinates in
device px**. Tiles are rasterized from SVG into a `CanvasTexture` at the tile's
actual pixel size (1:1), so they're always sharp; on resize — the layout is
recomputed (`computeLayout`), textures are re-rasterized (`rasterizeTiles`,
guarded to skip when the size is unchanged) and tiles/UI are repositioned
(`handleResize`, 120ms debounce). SVGs are loaded as blob-URL Image objects
(not `<img src>` — otherwise the canvas gets tainted) with injected
`width`/`height` (Adobe SVGs without them have zero intrinsic size).

## Fix after the first review (tile offset/overlap)

The first version of the renderer placed every full-size sprite edge to edge
(grid step = full tile size, no overlap). It turned out the Cangjie6 sprites
contain not just the face but also a drawn side face **above and to the right**
of it (measured pixel-by-pixel on `Man1.svg`: the face ends at ~84.4% of the
width / ~89.1% of the height, the rest is the side face + black outline). With
zero overlap, that neighboring tile's side face + outline remained fully
visible as a solid strip (~16% of the width / ~11% of the height) — that's
exactly what looked like "too big a gap, can't tell who overlaps whom," even
though the bounding boxes did touch (checked with `getBounds()`: the gap was
exactly 0px).

Fix (`static/game/render-constants.js`, `static/game/main.js`):
- **`STEP_X_FRAC = 0.80`, `STEP_Y_FRAC = 0.85`** — the grid step (distance
  between centers of neighboring tiles) is now SMALLER than the full sprite
  size; a neighbor overlaps this tile's side face and hides it (as in
  kmahjongg).
- **The depth formula was flipped**: in this art the side face is
  above/to the right (not below-left, as in the old hand-built body), so a
  tile with a SMALLER `y` and LARGER `x` is now drawn on top:
  `z*10000 + (HEIGHT-1-y)*100 + x` (was `z*10000 + y*100 + (WIDTH-1-x)`).
- `computeLayout`: the `wSpan`/`hSpan`/`contentW`/`contentH` formulas were
  recomputed based on the `stepX`/`stepY` step instead of the full
  `tileW`/`tileH` (otherwise the board either didn't fit or left extra
  empty space).

Verified: `getBounds()` before/after; a zoomed screenshot of two touching
tiles (the seam is clean, faces are readable); resize at 760×900 — the board
reflows and the overlap stays correct; `node --test` (22) + `manage.py test`
(47) — unchanged.

## Second fix: half-tile grid (the freedom rule was incorrect)

After fixing the overlap, a deeper problem surfaced: the peak and the
"head/tail" protrusions were being rounded to the nearest whole cell (because
`WIDTH`/`HEIGHT` were in "tile" units, where a neighbor is a step of 1). This
was **not just a visual inaccuracy** — the freedom rule (`is_free_position`)
compared coordinates exactly, so the rounding changed which tiles count as
neighbors in gameplay.

We read the authoritative source — the kmahjongg code itself
([`src/gamescene.cpp: isSelectable`](https://invent.kde.org/games/kmahjongg/-/blob/master/src/gamescene.cpp),
[`src/boardlayout.cpp`](https://invent.kde.org/games/kmahjongg/-/blob/master/src/boardlayout.cpp)):
there, coordinates are in **half-tile units** (a tile = 2×2 cells of such a
grid), regular tiles sit on EVEN coordinates, and the peak/protrusions sit on
ODD ones, in the same coordinate system, with no rounding at all. The rule:
- **Covered from above?** — a 3×3 cell window around the tile on the layer
  above (not an exact match) — so a corner tile shifted diagonally (like the
  peak's apex) still correctly covers it.
- **Free side?** — a column exactly 2 cells to the left/right, but with a
  tolerance of ±1 in the row — so a neighbor shifted by half a row
  (head/tail protrusions) is still seen correctly.

Ported 1:1 into `gameplay/board.py`/`static/game/board.js`:
- `WIDTH=30, HEIGHT=16` (half-tile units; previously 14×8 in tile units).
- `target_positions()`/`targetPositions()` now returns **coordinates taken
  verbatim from the primary source** (`_TURTLE_CELLS`/`TURTLE_CELLS`,
  transcribed from `cheshire137/Mahjong turtle.txt` and cross-checked against
  `KDE/kmahjongg default.layout`) — with no manual bitmap drawing at all.
  This also uncovered and fixed an error in the previous manual shape: the
  real width is 15 tile columns (30 half-units), not 14; columns 1/2/11/12
  have "jagged" edges (not full height), which the approximated version
  lacked.
- `is_free_position`/`isFreePosition` — a 3×3 window (covered) + ±2/±1 (side),
  instead of an exact coordinate match.
- `generator.py: is_adjacent` — adjacency is now based on a step of 2 (not 1).
- Rendering (`main.js`): `tileScreenPos` halves the grid step (2 half-units =
  1 tile step) and centers the tile at `+1` unit from the corner — correctly
  centering odd positions (peak, protrusions) too, with no special cases.

Verified: a new test, `is_free_position_above_tolerates_half_tile_offset`
(the peak's apex `(13,7)` correctly covers all 4 base tiles at
`(12/14,6/8)`, despite the lack of an exact coordinate match) — exactly the
scenario that previously worked incorrectly; 24 client-side + 49 server-side
tests; 90 generator configurations (30 seeds × 3 levels) are solvable;
visually — the peak is centered, the layers form a compact pyramid (checked
against a real kmahjongg screenshot).

## Third fix: the offset between layers — down-left, not "none" or "up-right"

After moving to the half-tile grid, the offset between layers was initially
removed entirely (all z on the same x,y — the only difference carried by
depth sorting + tint), because the previous offset (up-right, an arbitrary
constant of 0.11/0.13) smeared the peak diagonally on the new dense grid. But
with no offset at all, the stack looks flat — an offset is indeed needed,
just in the **correct direction and size**.

The artist (Cangjie6) drew the tile's thickness ABOVE and TO THE RIGHT of the
face — meaning the "camera" is positioned so that the side of the tile
closest to the viewer is bottom-left. A tile on a higher layer is physically
closer to the viewer (it sits higher in the stack), so on screen it should
shift in exactly that direction — **down-left**, and by exactly the size of
that same drawn side face (`render-constants.js`, measured pixel-by-pixel:
`LAYER_DX_FRAC=0.099` of the width, `LAYER_DY_FRAC=0.059` of the height — the
same proportions already measured for `STEP_X_FRAC`/`STEP_Y_FRAC`). That way
the exposed part of a tile under a higher layer (the triangle at top-right)
has a width of exactly one "thickness" — with no extra over- or under-overlap.

`tileScreenPos`: `x -= tile.z * layerDX`, `y += tile.z * layerDY` (was
`x += tile.z*layerDX; y -= tile.z*layerDY` — the opposite direction and an
arbitrary magnitude). Verified visually: the peak and stacks read as a
compact pyramid, and the exposed "steps" between layers match the drawn
thickness.

## Fourth fix: x/y weighting in depth sorting (a gap at the seam with the background)

After moving to the half-tile grid, in one specific spot — the seam between
the "head" protrusion `(0,7)` and its diagonal neighbor `(2,8)` (the only
real pair of same-layer tiles that differ by ±1 on BOTH axes at once, rather
than exactly 2 on one axis) — the background showed through the gap between
the tiles.

The cause was the formula `z*10000 + (HEIGHT-1-y)*100 + x`: the `×100`
weight for y completely "drowned out" the contribution of x. For regular
neighbors (differing by exactly 2 on only ONE axis) this didn't matter — the
other axis is the same, so the weight is irrelevant. But for `(0,7)` versus
`(2,8)`: the difference in y (−1 × 100 = −100) exceeds the difference in x
(+2 × 1 = +2), so `(0,7)` was drawn ON TOP OF `(2,8)`, even though it should
have been the other way around — `(2,8)` (further right and lower) should
have hidden the rounded bottom-right corner of `(0,7)`.

Fix: equal weight for x and y — `z*10000 + (HEIGHT-1-y) + x` (no `×100`). For
the two orthogonal cases (shared row/shared column) the result doesn't
change (there, only one axis ever differs). For diagonal half-tile adjacency,
the correct combination now wins. Verified visually (the head/tail seam on
the Turtle layout — no gaps), 24 client-side + 49 server-side tests, removing
a pair through the UI.

## Consequences / verified

- Server: 44 tests (`uv run manage.py test gameplay`) — 144 is solvable on 30
  seeds × 3 levels, composition 34×4+8×1, wildcard, `/start`→144, `/finish`
  validates a full solution including bonus pairs.
- Client: 22 tests (`node --test 'tests/*.test.js'`) — 144, 5 layers, `matchKey`.
- Browser (Playwright): the board with the peak renders; flowers/seasons are
  visible; both regular and **wildcard** (Spring+Winter) pairs can be removed
  through the UI; resize reflows + re-rasterizes without errors.

## Removed

- The texture atlas (`static/game/tiles.webp`, `tiles.json`) and
  `scripts/gen_tile_atlas.py` — the game rasterizes SVG at runtime, so the
  atlas is no longer needed.
- The baked body and its constants in `render-constants.js`
  (`DEPTH_X/Y`, `CORNER_R`, `FACE_W/H`, `GAP`, `SIDE_*`).
- The old FluffyStuff PNGs remain only as a source for `scripts/gen_icons.py`
  (`Front.png`+`Chun.png`); the icons themselves were not changed.

## Out of scope

- Precise difficulty calibration on the 5-layer shape (the top layer is small
  again) — the tests only require solvability; the "feel" of hard can be
  tuned later.
- DPR>1 was not tested directly in the headless browser check (dpr=1); the
  code multiplies all values by `this.dpr`.
- **Noticed (not fixed)**: if a `resize` event fires WHILE the deal-in
  animation (`playDealIn`) is running, `relayoutTiles()` forcibly repositions
  and resizes every tile that hasn't landed yet (not marked `_flying`), which
  can leave them visibly "stuck" at `alpha=0` until the animation ends.
  Doesn't happen under normal use (the window is rarely resized exactly
  within those ~1.5s after a game starts); reproduced only by deliberately
  resizing right after clicking "New game" in an automated test. Worth a
  dedicated fix (e.g. marking tiles still flying during deal-in with the same
  `_flying` flag) if it ever occurs in real usage.
